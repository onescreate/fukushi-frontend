# 10. 統合とハードニング計画（会計ポータルへの取り込み）

> 目的：福祉システムを One's Group の会計ポータル（noukigu / KGI / 研修 と同じ立ち位置）に
> **プロダクトとして統合**し、監査で判明した具体バグを潰して「超一流」品質へ引き上げる。
> **フルリライトはしない**（監査結論：既に設計書の約8割を実現した良い実装。作り直しは過剰かつ高リスク）。

## 決定事項（合意済み）
- **マルチテナントは維持**（他社提供想定。法人→店舗→利用者/職員の機構を活かす）
- **DBは福祉専用の別データベース**（同一Cloud SQLインスタンス上）。会計とはテーブル共有しない
- **認証は共有**（同じFirebase `business-management-753`。同一ログインは達成済み）
- **露出は「福祉」権限フラグ**で制御（会計側にモジュール権限を1つ新設。KGI等と同じ発想。付与者だけ切替に表示）
- **方針＝堅牢化＋統合＋“本当に酷い所だけ”作り直し**（KioskPage・フォーム系ダイアログ・共通util）
- **会計本番リポジトリは原則不可侵**（唯一の変更＝ポータルへの切替エントリ追加。追加のみ・権限＋URL未設定なら不可視）

## 監査で見つかった主な潜在バグ（“どこにバグか分からない”への回答）
### 🔴 請求の正確性
- 税が **軽減8%ハードコード**（バック `tax-util` / フロント `InvoicePrintPage`）。標準10%が一切適用されない／キャンセル料が非課税固定／品目別の標準・軽減が未実装
- 月締め `billing.close()` が **非トランザクション**（部分締めの事故）
- **全店舗ビューが締めを無視**（締め済みでもライブ集計→数字の食い違い）
- `closedSnapshot` が `as unknown`（型・検証なし）
### 🟠 打刻・日付
- 日付/TZが手作り＆不統一（UTC深夜 vs ローカル／TZ二重適用）→ 日境界のズレ
- `getAlerts` が **読み取り経路(kiosk board)でDB書き込み**＋N+1
- 遅刻/早退フラグが手修正・飛び込み時に**再計算されない**
- 日付クエリ未検証（`new Date(string)` 直渡し）
### 🟡 セキュリティ/堅牢性
- **TenantGuardが無い**（テナント分離が各サービスへのコピペ依存）→ 書き忘れで他テナント漏洩の構造リスク
- kiosk PINロックが**メモリ内**（Cloud Run複数インスタンスで無効）／`KIOSK_TOKEN_SECRET ?? ''`（空文字署名フォールバック）
- 食事一括予約が非トランザクション／`@Public GET /health/db` がテナント件数を漏らす
### フロント整理
- 重複ヘルパー（`pad`×15, `yen`×7, `isAll`×11）／フォーム抽象なし（300行ダイアログ）／KioskPage 539行の命令的機械／axios共通エラー処理なし／Dashboardが`<RosterPage/>`を内包／60sバッジpoll×4
