# Phase 0 実装計画 — 安全な土台づくり

> 作成日: 2026-07-02 / 前提: [01_システム設計書.md](01_システム設計書.md) 合意済み
> 進め方: **各ステップごとに確認しながら丁寧に進める**（推測で進めない）。1ステップ完了→動作確認→次へ。

## この Phase のゴール

「まだ機能は無いが、**安全で崩れない土台**が立っていて、ログインが通り、フロントとバックが正しくつながっている」状態を作る。ここが今回の作り替えの心臓部（既存に欠けていた認可・マルチテナント・マイグレーション・レイヤ分離）。

**完成時に動くもの:**
- Firebaseでログイン → バックエンドがトークンを検証 → 「あなたは誰で、どの法人/店舗の、どの権限を持つか」を返す
- その情報でフロントが認証済み画面の枠を表示する
- DBに法人→店舗→利用者/職員の土台テーブルがマイグレーションで作られている
- 共通UI部品（ボタン/セレクト/モーダル等）がデフォルト排除・統一デザインで用意されている

## 確定済み前提

| 項目 | 決定 |
|---|---|
| 作り替え方 | 新規に作り直す（既存コードはgitタグで温存し参考資料に） |
| 既存データ | 全てテスト用 → 破棄。データ移行は不要 |
| 環境 | ポータルのFirebase・GCPが存在 → 共有する |

## ステップ分割（各ステップで確認）

### Step 0-1｜準備・退避
- 既存コードを **git タグ（例 `legacy-v0`）** で保存 → いつでも見返せる状態に（消さない）。
- フロント/バック各リポジトリの新構成の土台を用意。
- **私からの確認事項リスト**（下記「必要な情報」）を洗い出し。
- 成果: 既存が安全に温存され、作業ブランチが立つ。

### Step 0-2｜バックエンド雛形（NestJS）
- NestJS プロジェクト初期化（TypeScript）。
- `/health` エンドポイント（生存確認）だけ作り、ローカルで起動確認。
- 成果: `npm run start` でサーバーが立ち `/health` が応答する。

### Step 0-3｜DB接続とマイグレーション（Prisma）
- **開発中はローカルの PostgreSQL（Docker）** を使い、Cloud SQL は後のデプロイ時に接続（安全・高速のため）。※Docker利用可否は要確認
- Prisma 導入。`schema.prisma` に**テナント&認証コア**を定義:
  `corporations / facilities / staff / staff_facility_roles / users / kiosk_devices`
- 最初のマイグレーションを実行（**破壊的DDL・手動SQLは今後一切使わない**）。
- 種データ（seed）: テスト用の法人1・店舗1・システム管理者1名。
- 成果: マイグレーションでテーブルが作られ、seedが入る。

### Step 0-4｜Firebase 認証連携（本人ログインの検証）
- バック: Firebase **Admin SDK** でIDトークン検証する **AuthGuard** を実装。
- `/me` エンドポイント: トークン→`firebase_uid`→DBのstaff/userを解決して「誰か」を返す。
- 成果: 正しいトークンなら200で本人情報、無効なら401。

### Step 0-5｜認可の土台（Tenant / RBAC ガード）
- **TenantGuard**（アクセス可能な法人/店舗をサーバーが決定）と **RbacGuard**（`@RequirePermission('...')`）の骨組み。
- ロール→権限のマッピング定義（設計書5.2）。
- 動作確認用に「権限が要るダミーエンドポイント」を1つ作り、権限有無で200/403が変わることを確認。
- 成果: 「サーバー側で権限・テナントを強制する仕組み」が実際に効く。

### Step 0-6｜フロントエンド雛形
- Vite + React + TypeScript を新構成で初期化。Tailwind 導入。
- Firebase **Web SDK** でログイン画面（職員/利用者）。※デザインは仮でOK、部品は後述キット。
- `apiClient`（axios＋トークン自動付与のインターセプタ）と **TanStack Query** 導入。
- **AuthContext**（ログイン状態・本人情報を一元管理。既存のバケツリレーを廃止）。
- 成果: ログイン → `/me` を叩いて本人情報を取得 → 認証済みの画面枠が出る。

### Step 0-7｜共通UIキット（デフォルト排除・統一デザイン）
- shadcn/ui を導入し、**Button / Select（コンボボックス）/ Modal・Dialog / 確認ダイアログ / Table / Input** の共通部品を整備。
- **ネイティブ `<select>` / `alert()` / `window.confirm()` は今後一切使わない**（設計方針）。
- カラー・角丸・影・余白のデザイントークンを1箇所に定義し全画面で統一。
- 成果: 以降の全画面が使い回す「洗練された部品箱」が完成。

### Step 0-8｜疎通・仕上げ
- ログイン→`/me`→認証画面表示までを通しで動作確認。
- GitHub へプッシュ。最小のCI（lint・型チェック）を用意。
- Cloud Run / Vercel への**初回デプロイは任意**（このPhaseでは必須にしない。ローカルで通ることを優先）。
- 成果: 土台一式が動き、リポジトリに入る。

## このPhaseで作る土台テーブル（Step 0-3）

設計書6章のうち、認証・テナントに必要な最小限:
- `corporations`（法人）
- `facilities`（店舗）
- `staff`（職員） / `staff_facility_roles`（職員×店舗×ロール）
- `users`（利用者）
- `kiosk_devices`（タブレット端末）

> 業務テーブル（予定/打刻/食事/請求/健康/加算）は Phase 1 以降で順次追加。

## 私から確認が必要な情報（推測で進めないため）

Phase 0 を進める中で、以下を教えていただく必要があります。**今すぐ全部でなくてOK**。各ステップの直前に、取得方法を私がご案内します。

1. **Firebase の設定情報**
   - フロント用: Firebase Web アプリの config（apiKey 等）
   - バック用: Firebase Admin SDK のサービスアカウント鍵（JSONファイル）
   - → 取得手順は Step 0-4 の直前に画面つきでご案内します。
2. **ローカル開発に Docker が使えるか**（Step 0-3）。使えない場合は代替（直接Cloud SQLの開発用DB接続など）をご案内。
3. **合成メールのドメイン**（利用者ログイン用 `{login_id}@____`）。ポータルと揃えるか、専用ドメインにするか。
4. **GCP / Cloud SQL の接続情報**（デプロイ時。Phase 0では後回し可）。

> セキュリティ上、鍵ファイル（サービスアカウント・DBパスワード等）は**リポジトリに入れず** `.env`＋`.gitignore` で管理します。
